# Verificación móvil

Implementado: Expo SDK 54 con React Native 0.81.5, módulos nativos compatibles fijados, billetera SQLite, claves del titular en SecureStore generadas por `expo-crypto`, firma y verificación Ed25519 de credencial y prueba de posesión, cámara, historial persistente de intentos y sincronización incremental.

`npm run test --workspace @hypernova/contracts` verifica firmas reales en Node, rotación temporal, revocación, transferencias con cambio de titular, permisos de evento y zona y rechazo de tokens manipulados. Las claves de prueba se generan aleatoriamente por ejecución. `npm run typecheck --workspace @hypernova/mobile` comprueba el código TypeScript estricto. La exportación de Expo para Android e iOS se registra con los resultados generales de QA.

`node scripts/check-hermes-crypto.mjs` construye un bundle de navegador sin APIs criptográficas de Node y lo compila a bytecode con el `hermesc` que incluye React Native. Guarda el resultado en `docs/qa/hermes-crypto.json`. En este entorno, el ejecutable incluido es exclusivamente un compilador: aunque su ayuda enumera `-exec`, devuelve explícitamente `hermesc does not support -exec`. El script devuelve código 2 cuando falta el runtime, para evitar confundir compilación con ejecución. Se puede proporcionar un runtime Hermes compatible mediante `HERMES_RUNTIME` para ejecutar las verificaciones dentro del motor.

Actualización manual del 16 de octubre de 2026: el autor confirmó login del asistente y del staff, billetera con QR, renovación a 25 segundos y lectura por cámara virtual en otro emulador con resultado «Entrada válida». La evidencia se compartió en la conversación; no se publican los originales porque incluyen credenciales y datos personales del escritorio. No equivale a una suite automatizada en Hermes ni a una prueba offline completa.

Pendiente: ejecución de la suite criptográfica dentro del runtime Hermes, persistencia SecureStore/SQLite tras reinicio, modo avión con dos escáneres independientes, revocaciones y rendimiento con miles de intentos. No hay APK terminado o video/GIF verificados. Compilar JavaScript y crear bytecode no prueban por sí solos la ejecución nativa.

La revisión de código identificó y corrigió carreras en la generación de idempotencia y renovación de sesión, duplicados al cambiar de puerta y un rechazo vacío que podía bloquear un lote. La obtención de clave de idempotencia y la admisión local usan transacciones exclusivas. Las operaciones de compra tienen una exclusión síncrona en la UI. Un intento local conserva el cursor de revocación y la fecha del snapshot; el tiempo se calibra con `serverTime`. Estas correcciones fueron revisadas estáticamente y necesitan el recorrido real en dispositivo para verificar el comportamiento de los módulos nativos.

Recorrido de aceptación pendiente: abrir billetera y turno con conexión, activar modo avión, admitir una entrada y rechazar el duplicado después de reiniciar; rechazar una captura de hace un minuto; sincronizar una revocación y rechazar la versión anterior; usar dos dispositivos offline con la misma entrada y observar el incidente al sincronizar; cambiar de puerta en el mismo teléfono y confirmar que el historial local mantiene el rechazo; probar reserva/pago con doble toque y respuesta perdida.
